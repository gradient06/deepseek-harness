# Agent Note：把文件拖入或粘贴到会话的工作目录

Status: implemented

[English](2026-08-23-composer-file-drop-into-working-directory.md) | 中文

## Problem

Web 输入框此前只能接收图片：拖入或粘贴的文件都会走草稿图片栏那条路，任何非图片 MIME 都会被以图片格式的文案拒绝。要把其他文件交给会话——一份待审的 PDF、一份待分析的 CSV、一段跑不起来的脚本——输入框完全没有路径。用户只能自己把文件拷进项目、跑一条 shell 命令，或者描述得足够清楚让智能体重建出来。与此同时文件停在浏览器里，而真正读取项目目录的会话工具根本看不到它。

## Decision

输入框通过 `POST /api/workspace-file?session=<id>&name=<name>` 把拖入和粘贴的非图片文件写入所寻址会话的工作目录，该路由由 web-app bundle 注册在本 fork 的 `/api/ocr` 路由旁边。路由返回 `{ name, path, bytes }`，其中 `path` 相对于会话目录；输入框随即在草稿里追加一行提及这些路径——法语下为 `📎 Ajouté au répertoire de travail : docs/notes.txt`——于是智能体用自己的工具读取该文件，而不是听一段散文描述。用户准备好的时候再发送这条消息。

会话 id 是请求携带的唯一凭据。目录来自宿主侧常驻的会话头（`ctx.sessions.get(id)?.header.cwd`），绝不来自客户端；`name` 必须是单个路径分量——分隔符、`.`、`..` 都会在任何写入之前以 400 拒绝。因此该路由无法寻址到会话自身项目以外的任何位置。已存在的文件永不被替换：名字被占用时 `notes.txt` 变成 `notes-1.txt`（最多 100 个候选），响应携带的始终是实际写入的名字。

图片继续走草稿栏及其自身校验；其他所有文件走写入路径。输入框里的一处分流同时服务两种可携带文件的手势——文档拖放（由附件插件经槽位的 `onAddFiles` 路由）与剪贴板粘贴——因此二者不会分叉。当输入框接收文件时，拖放邀请文案切换为文件措辞（`file.dropTitle` / `file.dropDesc`）。

路由把请求限制在 64 MiB 请求体与 255 字节文件名，并对未知会话返回 404、对头部没有 cwd 的会话（项目之前的旧日志）返回 409、对非 POST 方法返回 405。

## Alternatives considered

**把文件搭在图片附件通道上**（即以提交载荷中的 base64 形式，图片正是这样抵达宿主的）。附件存储在契约上只接受图片，而这里的目标是让文件出现在会话工具本就会读取的项目里——不是浏览器附件空间里的一个 blob。扩展那条通道还会为这个两者都不需要的用例改动提交线格式与已记录的用户消息。

**在 API 域表面上新增一个生成的 RPC 方法。** 类型化 RPC 映射是 harnais 的原生路径，能带来端到端的类型。代价是一份 schema、一次代码生成，以及为这个 fork 本地用途重建全部生成的客户端契约——而 `/api/ocr` 的先例已经用一条普通路由覆盖了同样的需求，因此本次以路由形式交付。

**写入后自动提交消息。** 一次手势完成交付与发送，点击更少，但它把提示词从用户手里拿走了：整条消息只剩这行提及，任何指令（「résume ce PDF」）都得变成第二个回合。改为把提及放进草稿，一次 Enter 同时送出两者。

**每次上传都询问目标目录。** 选择器让目标变得显式，但它问的是会话早已回答过的问题——其工作目录是它的工具唯一被限定作用域的根——而客户端提供路径会把「什么可以写到哪」的凭据从宿主搬到浏览器。

## Consequences

用户把文件拖到页面上、或从文件管理器粘贴过来，就把它交给了智能体；智能体在消息中点名的路径找到它，用户自己的编辑器看到的是同一个文件。写入有界且无法逃出会话目录，而请求唯一断言的东西仍然是会话 id。

这次写入本身不记录任何模型可见事件：文件出现在磁盘上，模型读到的是用户消息里的那行提及——与用户手打同样的文字别无二致。误写的文件就是普通文件：会话工具可以删除或覆盖它；而路由的后缀规则意味着重复上传永远不会毁掉先前那一个。

该路由信任的边界与这个 bundle 的其它所有 `/api` 表面相同，即环回/局域网；把 Web GUI 暴露到该边界之外，就等于把写入会话项目的能力交给任何能连上该端口的人，正如 `/api/ocr` 早已把 OCR 调用交了出去。
